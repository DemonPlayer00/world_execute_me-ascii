# world.execute(me); — TTY 粉丝 MV

把工作区里的 Mili《world.execute(me);》做成一支**在终端里播放的 MV**。
画面是字符与 ANSI 颜色，随音乐实时驱动；窗口多大就长多大，从 20×4 到 300×80 都不散架。

```
./play.sh
```

**没有播放器外壳**：没有顶栏、没有频谱条、没有歌词滚屏、没有常驻进度条。
整个终端就是画面本身。字幕也不是歌词流水账 —— 全片只有 **13 处、共 14 个词**出现在屏幕上（标题卡另算，它由 `title` 幕全程绘制）
（占时长约 10%），其余全部由图形表达。

（画面里**会出现**进度条，但它不是外壳：约四成的镜头带一条"执行进度"，
显示这首歌已经走了多少 —— 那是程序在给自己的执行计时。见第 1 节。）

## 1. 它长什么样

一支 3 分 31 秒的片子，按歌的**实测结构**分成 15 幕，讲一件事：
**一个程序和一个人的关系。**

这件事不靠字幕讲。画面里始终有**两个东西**：大的那个是「我」——每一幕画的主体；
小的那个是「另一个人」——一个带拖尾的亮点，像光标，像萤火虫，像房间里另一个人。
两个点之间的距离就是剧情。把位置单独读出来：

| 时间 | 剧情 | 画面 |
|---|---|---|
| 0:00 | 独处 | 冷启动，**按真实控制台的排布，整行整行地出现**（不是逐字打印）：dmesg 风格的 `[    0.550000]` 内核行、systemd 风格的 `[  OK  ]` 服务行、pacman 风格的 `:: Synchronising package databases...` 与 `(1/4) loading subject` 计数，外加一条 `[ WARN ]`；
**16 行带命令行内嵌进度条**（`[######------]  57%` / 下载行的 `MiB/s 00:08 [####] 100%` /
`[....]` 三种样式）；共 **49 行**，随窗口高度滚动。代码雨在背后，心跳波形在底部。屏幕上只有它自己 |
| 0:04 | **它来了** | 边缘处亮起第二个点，很远 |
| 0:16 | 两个，隔着很远 | 标题卡打在两人之间 |
| 0:29 | 它在演示自己 | 点集 → 立方体 → 圆 → 正弦 → 无穷符号，连续变形；另一个在旁边看着 |
| 0:44 | 靠近 | 正弦被拉平（交流→直流）→ 卷成螺旋（头晕）→ 星流（穿越）→ 两条波合拢（合为一体） |
| 0:59 | **相遇** | 副歌：两个点重合，同心圆环一圈圈推出去 |
| 1:14 | 仍在合一，不停变形 | **茄子 → 番茄 → 花猫 → 神**，依次溶解。它把自己说成什么，就变成什么 |
| 1:20 | 开始分开 | 日晷：太阳走过天空（AM→PM），两环交换位置（S↔M）。它自己已经退到画面外缘 |
| 1:43 | 走了 | 一群光点一个个离开画面 |
| 1:51 | 只剩它一个 | 「你走了」×5 之后，正中一个点，一圈涟漪 |
| 1:58 | 独自对抗 | 非法参数：世界网格开始错位、撕裂成一张坏掉的网 |
| 2:27 | 审判 | 铡刀一次次落下，**每落一次就在环上留一道疤**，十二次之后那张环已经伤痕累累；六语倒数用记数环 |
| 2:42 | 对着空房间喊 | 第二次副歌：同样的动作，环少了一半、带着缺口、还没到就散了 —— 没有人应答 |
| 2:57 | 爱 | 一颗心（就是歌词说它「知道」的那条代数曲线）。**小的那个在心的外面** —— 你自由，我困在里面 |
| 3:12 | 熄灭 | 器乐段：涟漪扩进虚空 |
| 3:25 | 关机 | 最后一次 `EXECUTION`，波形折叠成一条线，终端打印 `[ process terminated ]` |

### 藏在启动日志里的三个名字

机器（**Aperture**）、它跑在什么运行时上（**dsh**）、以及被加载的那个东西是谁写的（**Mili**）——
三个名字都不点名，各自以**真实启动会用的形态**出现几次，分布在内核行 / systemd 单行 /
包管理器行三种 register 里：

```
dsh_core: DeepSeek Harness runtime 1.30, agent=glados, profile=web
dsh_core: control loop attached, tools=17, journal=/var/lib/dsh
aperture_relay: panel 0xc0re online, 6 chambers enumerated
mili-fw: loading momocashew.bin for device 0000:00:1f.3
mili-fw: signature ok, vendor kasai audio lab
[  OK  ] Started dsh.service - DeepSeek Harness
[  OK  ] Started aperture-sound.service
[  OK  ] Mounted /opt/aperture (enrichment centre)
 aperture is up to date   /   dsh is up to date   /   mili is up to date
```

没有一行是在"介绍"它们 —— 都只是驱动名、服务名、路径名、包名。
`selftest.py` 断言**各自至少两种写法、且各自出现在不止一种 register 里**，
所以谁把它们删掉、或者挤成一行，测试会红。

### 三层结构：幕 → 场景 → 画面

15 幕只是**章节**，一章 5–30 秒。下面还有两层：

**场景层（`shots.py`）** —— 按**句意**切，不是按固定句数切：
一句话讲完（歌词推进到它一直在铺的那个大写词）就换一个场景。
句数上限 3、时长上限 3.6 秒只是防止某句跑飞。
得到 **65 个场景，中位数 3.3 秒，最长 4.5 秒**。每个场景重新调度一次画面：

- **背景母题**：从 16 种矢量母题里抽（轨道 / 玫瑰线 / 利萨茹 / 环面 / 隧道 / 晶格 /
  摩尔纹 / 螺旋 / 星形 / 波栅 / 花瓣 / 三叶结 / 放射刺 / 蛛网 / 星系 / 星座），
  **洗牌发牌**，保证同一个母题不会连续出现两次，也不会形成可预测的循环。
- **机位**：zoom（6 档）× 旋转（6 档）× 镜像 × 平移，每个镜头不同。
- **点缀**：环 / 爆裂 / 横扫 / 网格 / 尘埃，轮换。
- **超出画面的元素**：约 45% 的场景会在画面外再放一份**放大到 1.7–2.4 倍**的母题，
  只有一小块碎片落在框内；另有 1–3 条**贯穿线**从画外一侧穿到另一侧，各自按不同速度漂移。
  全都刻意大于屏幕 —— 所有东西都规规矩矩待在边框里，读起来是示意图，不是一个地方。

**相位层（`figures.PHASES`）** —— 长时间的那几幕不只是"一张图放很久"，而是**按句意拆成多个场景**：

| 幕 | 时长 | 拆成 |
|---|---|---|
| `argument` | 28.7 s | **4 段**：碎片散开 → 晶格开裂 → 世界撕裂 → 残骸漂浮 |
| `love` | 17.2 s | **4 段**：心形 → 被丈量（一道道弦） → 化成代数曲线 → 困在里面 |
| `chorus` | 14.8 s | **4 段**：刺激 → 满足（环变成轨道） → 执行（环变成刀） → 收拢 |
| `geometry` | 14.7 s | 5 段（点/立方体/圆/正弦/无穷） |
| `current` | 14.8 s | 5 段（交流/直流/眩晕/穿越/合一） |
| `menagerie` | 14.5 s | 4 段（茄子/番茄/猫/神） |
| `void` | 11.4 s | 3 段（向外/向内/静止）—— 器乐段没有词，按实测段落切 |

有新词的幕，**每一段的起点都精确落在官方歌词行上**（`selftest.py` 断言）。

### 故障时的屏幕撕裂

歌里有三段机器正在崩坏：**非法参数**（含判决挂起的那 16 秒）、**历次执行**、以及**最后一次执行**。
这三段会真的撕屏 —— 不是"闪一下"，是**画面滑位**：

- **垂直滚动**：整帧向下滑几行（垂直同步失锁）
- **撕裂线**：画面被切成若干片，每片横向错开不同距离。单片错位看起来只是"挪了一下"，
  **一串错位才像画面丢了位置**
- **重复带**：某一条带被复制到别处，就是"撕开的帧"那个标志性的重影

三种都是**纯水平位移**，所以没有凭空编造内容 —— 帧还是那一帧，只是不在它该在的地方。

**触发点不是节拍**，而是 `TEAR_EVENTS`（12 个时刻，**每一个都对应那一句的官方歌词时间戳**）
加上该段的下限 `TEAR_FLOOR`。理由写在代码里：**每次重拍都滑一下是节拍器，不是故障。**
音乐越粗糙画面越不稳（跟着 flux/高频平滑走），但不是跟拍。

实测：判决段 36/36 行位移、最大错位 6 格；执行段 36/36 行；
而 geometry / love / transform 这些正常段落 **0/36 行位移**。

**人声断音时也撕一下，但是短的。** 歌里的断音是**写下来的**：一行里重复的词、
连续三行说同一件事、以及一个故意用连字符拆开的字母串。所以断音是从**歌词本身**
读出来的，共 **14 处**；每处触发一段 **300 毫秒**的撕裂，全曲只占 2.0% 的帧 ——
断音是切掉的一个音节，不是机器故障，所以它短。

> 这 14 个时刻现在住在 **`mv/ttymv/tears.py`**，和失败瞬间、重置闪光放在一起，
> 是整个撕裂机制唯一的输入。理由见下面「撕裂时间轴」一节。

试过用音频检测（中频段 180 Hz–3 kHz 的短时凹陷），**在这个编曲上不可靠**：
它找到的其实是合成器在让位（前奏 0–30 秒有 41 处，而人声最密的副歌 60–90 秒有 0 处）。
中频凹陷只作为**加码**：若有实测凹陷正好落在同一时刻，撕裂更狠一点，但不由它决定位置。

### 故障结束后的“重置”

每一段长时间的撕裂结束时，屏幕会**整屏刷白一下**再回来 —— 模拟机器复位：
面板底色推到 hot 色、字形同时压向底色，画面是**洗掉**而不是单纯变亮
（一块只有一种多余颜色的屏幕上，复位就是这个样子）。

全片**只有三次**，都在长故障段的收尾：判决残骸散尽、刀锋将起时（147.660）；
历次执行结束、末段副歌将起时（162.632）；以及最后停机时（207.481）。
**踩在拍上的闪是频闪，故障清除时闪一次是复位。**

### 边缘闪现的小字

除了那 14 个大词，还有**一层小字**（`FLASH_CUES`，26 条）：一次一个词，
**用 3×5 微字体**（`font.TINY`，一个字母 3 格宽 —— 大字体是 5 格），
**固定落在画面外圈的八个锚点之一**（四角 + 上下中 + 左右中），
永远不会出现在正中间 —— 中间是主体的位置。
另外：**速度很快、字很短**，是"闪过一下"而不是阅读材料。
淡入淡出各 0.18 / 0.30 秒，所以是"闪现"而不是字幕。
用的词仍然取自**没用过的官方歌词行**（PROTECTION / CIRCUMFERENCE / NUTRIENTS / ALGEBRAIC …）。

### 进度条：不是播放进度

约 **四成镜头**（32/72，共 52 条）带进度条，而且**一条镜头里可以有多条**
（1 条 16 个镜头 / 2 条 12 个 / 3 条 4 个），长短粗细各不相同
（长度 6 档 0.42–1.00，粗细 5 档 0.7–1.8，高度 6 档）。

**每一条读的都是乐曲或剧情里真实发生的事**，没有一条是"这首歌放了百分之几"：

| 语义 | 它表示什么 |
|---|---|
| `section` | 走到本幕的哪里（音乐结构） |
| `phrase` | 走到本镜头这句歌词的哪里 |
| `story` | 另一个它离得有多远（剧情） |
| `cue` | 正在填向下一次开口唱的那一刻（期待） |

**故意不含任何跟拍的东西**：早先的 `beat`（四拍扫一次再弹回）与 `energy`（跟着瞬态跳）
会让进度条看起来像音量条，已经删掉。留下的四种只会平滑或单调地走。
`selftest.py` 有一条防倒退断言盯着这件事。


场景进度条的**语义、长度、粗细、出现时段全部固定**，只有**角度与高度**是随机化的 ——
而且是**连续随机**而不是从短列表里挑：早先只有 10 个角度 × 6 个高度，
72 个镜头下来同一批组合会反复出现。现在：
- **平放是少数（13%，7/52）**，而且是**按构造定数**而不是逐条抽签 ——
  逐条抽签时 n=52 的运气偏差会让实际比例飘到 35%。其余取 `±[0.13, 0.85] rad`（约 ±7.5°–49°）的连续值，
  下限 0.13 是为了**避开"看着还是平的"那段灰带**；倾斜角几乎两两不同。
- 高度落在上下两条带里（`|y| ∈ [0.46, 0.88]`），**让开画面正中**（主体在那儿），
  同一镜头的多条按槽位错开，不会叠在一起。

**外面有框**：每条进度条都套一个沿条身躺着的矩形外壳，看起来像仪器而不是一条走线的噪点
（52 条里 41 条带框）。进度条画在**最上面的仪表层**、与第二个实体同层 ——
字幕压不住它、也不会被字幕的变暗逻辑冲淡。

可以**平放**（angle 0）也可以**倾斜**（±8°/±15°/±23°/±36°）。
因为盲文点各向同性，任何倾角、任何终端尺寸都是实心条。

镜头边界**不是随手切的**：每一条都精确落在已发布歌词的某一行上
（`selftest.py` 断言）；器乐段没有歌词，就吸附到**实测的 130 BPM 拍点**上。
母题画得比主体更大、更暗、更稀（点线），是"这个镜头所在的房间"，而不是第二个主体。

每一幕另外还有**自己的背景质感**（雨 / 星野 / 制图网格 / 流场 / 会聚射线 / 抖动场 /
日晷辐条 / 坠落光点 / 数据噪声 / 铡刀幕帘 / 心跳波纹 / 空洞射线 / 塌缩线），
粒子也各有各的行为（会聚 / 离散 / 环绕 / 漂移 / 溅射）。

标题卡 `WORLD.EXECUTE(ME);` 由 `title` 幕从 16.000 一直画到本幕结束（约 13 秒），
**只此一次**；其余 13 处、共 14 个词（全部落在官方歌词时间戳上）：


## 1.5 字符：不只是点

盲文给每个格子 **8 个可寻址的点**（2 宽 × 4 高），所以这个片子的图形全是用点堆出来的 ——
但**整幅画只有一种笔触，画什么都是同一种质地**。`mv/ttymv/ink.py` 补上字符网格的
另外半套词汇：

| 能力 | 怎么做的 |
|---|---|
| **线条** | `LineCanvas` 记住一格的四条边哪几条进了线、那条线多重，然后选对应的字符。转角、丁字口、十字口**自己就出来了** —— 调用方不需要知道它们存在 |
| **加粗** | 字符网格画不出更粗的笔画；它能做的是**同一格换一个更重的字符** —— `─` 和 `━` 是同一条线的两个重量，`═` 是第三个。这就是这里唯一诚实的"加粗" |
| **纹理** | 一组 ramp（`▁▂▃▄▅▆▇` 高度填充、`▏▎▍▌▋▊▉` 宽度填充、`·˙•°○●` 灰阶、`╱╲╳` 斜线……），让密度可以画成阴影、填充或颗粒，而不只是"点堆得多不多" |
| **动态** | `ramp_char(..., boil=)` 让一格**按自己的哈希**在时间上跟邻格换位，画面几何停下来之后质地还在动 |

### 每个字符都先查过字体

视频是用**这台终端自己的字体**渲染的（见 3.5），所以字体没有的字形不是"回退一下"而已 ——
要么变成别人的形状，要么直接是豆腐块。box-drawing 一共 128 个字符，
文泉驿等宽微米黑 Mono **有 113 个**：轻线、**重线**、双线，以及**轻重混排**
（`┍┎┞┠┭┰` ……）全都在，而且**宽度全是 0.6016em**，正好一格。
只缺半线端头（U+2575–257B）和虚线竖笔 U+254C–254F。

> 最后这个缺口是有代价的：背景原来用 `╎`（U+254E）画虚线栅格，字库里没有，
> 于是**每一个竖笔都要去别的字族取字形**。换成 U+2506 `┆` 之后既是本族字形，也更重。

**`█` 只给文字用**，这是一条硬规则（`ink.assert_no_type_block` 在 import 时就查）：
标题卡、字幕、日志的进度条、代码雨的头部都用它。纹理 ramp 因此**都在满格前一步停住**
（`▁▂▃▄▅▆▇` 而不是 `▁▂▃▄▅▆▇█`）—— 否则屏幕上会出现"看起来像字"的东西，
而且"画面上有多少字"就没法从外面量了。

### 谁用哪种笔触

不是每一幕都换，也不全都换：

| 幕 | 笔触 | 为什么 |
|---|---|---|
| 几何 / 参数 / 论证 / 执行 | 盲文点 | 猫、茄子、心是**剪影**，一格一个点会糊成一团 |
| current / loss / void | `·˙•°○●` | 这些是**天气不是物体**，没有剪影，只有方向 |
| end | `▁▂▃▄▅▆▇` | 一切塌回一条水平线，用"高度填充"正好 |
| transform | `·+×○◇◆●■` | 日晷/机械，需要读起来像器械 |

线层另外**全片都在跑**：主体外面那圈取景框、扫过画面的长线、网格重音、
日志的框、进度条的外框，都走线层。两层**各取对方没占的格子**，所以是交织而不是覆盖。

### 背景线条不再发虚

三件事一起改的：字符换重（`┆`/`━`/`┃`）、混色提亮（从 0.05–0.16 提到 0.14–0.26）、
以及**别用密度换可见度**。最后一条是关键：线层一开始每行都画规则，
结果整帧变成一张网，主体没地方画了。现在的取值是**稀疏但重** ——
`flow` 每 3 行一条虚线、`dither` 每 4 行、幕帘每 7 列一根。

**量过的**：held shot 里每帧约 **30%** 的亮格换字符，其中**只有 1.25 个百分点来自 `boil`**
（31.12% vs 29.87%）—— 其余是几何本身在动。也就是说动态字符是**在动的画面上再加一层呼吸**，
而不是把静止画面抖成噪点。

## 2. 它怎么工作

三层，各自的**数据来源完全不同**，这一点很重要：

### ① 声音 → 数字（全部实测）

`mv/ttymv/analyze.py` 用 ffmpeg 解码，做一遍 STFT，把整首歌量成一张 700 KB 的缓存表
（`mv/cache/*.npz`，首次运行自动生成，约 1 秒）：

- **56 个对数频段**的能量（20 250 Hz 窗，50 帧/秒，共 10 592 帧）
- RMS、谱通量（onset）、谱质心、低/中/高频段能量、L/R 立体声
- 300 Hz 的波形 min/max 包络（给示波器用）
- **417 个瞬态点**（谱通量峰值 + 抛物线插值，亚帧精度）
- **21 个段落切点**（checkerboard novelty 曲线，再吸附回最近的瞬态）
- **速度：130.000 BPM**，拍相位 0.1254 s

这些数字全部来自这份 .ogg 本身，没有一个是我估的。

### ② 歌词 → 时间轴（有出处）

`lyrics/world.execute(me).lrc` 是**这首录音的官方时间轴歌词**，
来自网易云曲库 track `435278010`，时长 211906 ms —— 与工作区里这份 .ogg（211.91 s）
是同一版母带，所以时间戳可以逐字对齐，不是"大致的"。

只保留英文原文，不含翻译轨。

### ③ 画面（我写的）

`mv/ttymv/figures.py` 是这支 MV 真正的主体：形状库 + 变形 + 溶解。

所有图形都是**归一化空间的点云**，再描进盲文层，因此同一份代码在任意终端尺寸下都成立。
两个让这件事变便宜的事实：

- **盲文点是各向同性的**。一个字符格是 2 点宽 4 点高，而终端格子高度约为宽度的两倍，
  所以一个点在横竖方向上等距 —— **圆画出来就是圆**。对一首讲几何的歌来说这很合适。
- 点云先于像素存在，所以放大缩小不需要任何特判。

`mv/ttymv/story.py` 是那条故事线：第二个实体的路径是**手写的**，不是生成的，
每个关键时间点都对着一处实测切点或官方歌词行。它只提供位置与透明度，
剩下的事交给画面 —— 距离本身就是台词。

`mv/ttymv/motifs.py` 是 16 种矢量母题的库；`mv/ttymv/shots.py` 把它们按歌词切成 72 个镜头，
并用洗牌发牌避免重复。

`mv/ttymv/scenes.py` 负责调色板、幕表、背景质感、粒子和排版；
它消费的仍然是上面那两层数据 —— 每个视觉事件都挂在实测数字上（拍、瞬态、段落切点）。

**文字是导演，不是转录。** `TEXT_CUES` 是一张手挑的cue表，
每一个时间戳都取自已发布歌词的对应行（`mv/tools/selftest.py` 会断言这一点，
所以"只挑一部分"不等于"脱离人声"）。

## 3. 终端适配

没有外壳要腾地方，**舞台就是整个终端**，任何尺寸都一样。
剩下要决定的只是这个尺寸能承载多少细节：

| 尺寸 | 行为 |
|---|---|
| `20×4` / `30×8` | 图形自动缩小；罕见的文字退化为终端自带字体的普通文本（分行，不切词） |
| `46×12` | braille 图形完整，粒子场精简 |
| `80×24` | 经典尺寸，全部图层 |
| `120×36` | 图形直径约 33 格宽 × 17 格高，笔画密度舒适 |
| `160×48` / `200×56` | 大字 scale 3–4，字距按屏幕格收紧（不随点阵等比放大） |
| `260×70` | 19 ms/帧，仍有 52 fps 余量 |

**按终端能力自动降级**（读 terminfo，不靠猜 `$TERM`）：

| 环境 | 颜色 | 字形 | 帧率 | 备用屏 |
|---|---|---|---|---|
| Konsole / xterm / VTE（真彩） | `true` | `braille` | 30 | 用 |
| 只有 256 色的终端 | `256` | `braille` | 30 | 用 |
| **Linux 虚拟控制台**（`TERM=linux`） | **`16`** | **`block`** | **20** | **不用** |

虚拟控制台和图形终端是两种东西，硬套一样的输出会坏：

- **它没有备用屏**。`linux` 的 terminfo 里根本没有 `smcup`/`rmcup`，`ESC[?1049h` 会被**静默忽略**，
  于是每一帧都画在主屏上、往 scrollback 里灌。现在没有备用屏就不进，改为进入和退出各清一次屏。
- **它只有 8/16 色**，而且真彩 SGR 不是"被忽略"这么简单：内核 VT 是**逐个参数**解析
  `ESC[38;2;R;G;Bm` 的，于是 `2` 被当成「暗淡（dim）」、后面三个数被丢掉 —— 画面会整体变暗且没有颜色。
- **它藏光标要 `ESC[?1c`**（恢复 `ESC[?0c`），光发 `ESC[?25l` 不够。
- **它没有 Braille 区**，所以自动换成 `· : + * #` 点阵。

**其他自适应**：

- `SIGWINCH` 实时重排，窗口拖动过程中就跟着变。
- 慢终端自动跳帧：落后就丢掉错过的帧，而不是猛刷。
  **画面每帧都按音频时钟现查**，所以跳帧只降流畅度、不失同步；`--stats` 可以看丢了多少。
- `--altscreen/--no-altscreen`、`--sync/--no-sync` 可手动覆盖。

## 3.5 渲染成视频（用本机终端的字体）

MV 本来是**这台机器上的终端**里的动画，所以把它拍成视频，唯一诚实的做法是用
**这台终端的字体** —— 不是"随便一个等宽字体"。而这台终端的字体不是口味问题，
它是**写下来的**：

```
~/.config/kdeglobals   [General]
fixed=文泉驿等宽微米黑,10,-1,5,400,0,...
```

Konsole 没有自己的 profile（`~/.local/share/konsole/` 里没有 `.profile`，`konsolerc`
也没有 `DefaultProfile=`），于是它继承 KDE 的全局字体。`kfont.py` 负责把这条配置
还原成像素，每一步都实测：

| 步骤 | 结论 | 怎么定的 |
|---|---|---|
| family / 字号 | `文泉驿等宽微米黑` @ 10pt | 读 `kdeglobals` 的 Qt 序列化字体串（`pixelSize=-1` → 由字号推） |
| px | **13px**（10pt @ 96dpi） | Qt 的取整规则 |
| **字面（face）** | `wqy-microhei.ttc` **index 1** | 该 TTC 的 face 0 是比例体、face 1 才是 Mono；终端必须用等宽面 |
| **格子** | **8 × 15 px**（纵横比 1.875:1） | 直接问 Qt（`QFontMetricsF`）。**不是 2:1** —— 见下 |

```sh
python3 mv/tools/kfont.py                    # 打印字体、格子、每个字符用哪个 face
python3 mv/tools/kfont.py --scale 4 --rows 54
```

### 为什么格子是 1.875:1 而不是 2:1

MV 的点阵几何假定"一格 = 2 点宽 × 4 点高"，也就是 2:1。真终端不是：
Qt 把**步进**和**行高**分别取整，13px 处得到 8×15。这是取整的产物
（连续值是 0.6002em : 1.1538em ≈ 1.922），但在 13px 它确实是 **1.875**，
而 Konsole 就是这样画的。渲染器**保留终端的真实格子**，所以画面里圆点会
比作者假定的略扁一点 —— 和你在 Konsole 里看到的一模一样。

倍数放大时这一点会漂（39px → 23×46 = 2.000），所以格子始终取**原生格子的整数倍**，
而不是重新问 Qt。

### 字体缺字怎么办

WQY Micro Hei Mono 缺的正好是这些：**盲文 U+2800–28FF**、`╎ ░ ▚ ▞`。
眼下的选择不能靠"看着顺眼"，`kfont.py` 走的是 fontconfig 的**有序候选表**
（并且带 `spacing=100`，因为 Konsole 的字体是等宽的，替代字体也得是），
然后按**实测**淘汰：

| 淘汰理由 | 被淘汰的 | 实测量 |
|---|---|---|
| 根本没这个字形 | 大部分 face | cmap |
| **一个点画成八个圈** | **FreeMono** | 单点字形有 8 团墨 —— 它把 7 个*未选中*的点画成空心圈。它盲文步进正好 0.6000em、格子完美贴合，本来会赢下每一个盲文字符，但那会把整片点阵画面变成一片圆圈 |
| **点距波纹 41%** | Cascadia Code | 它的 4 行点只占行框的 55%，点挤在中间、纵向点距配不上横向点距 |
| 墨迹溢出格子 | Noto Sans CJK（`░ ▚ ▞`） | 字形整整 1em 宽，塞进 0.6em 的格子只剩左边 60% |
| 墨迹跑出行框 | Noto Sans CJK（`╎`） | 它的 ascent 更高，对齐基线后整体上移 13px，竖线接不上 |

活下来的组合：

```
WQY Micro Hei Mono   —— 它覆盖的一切（拉丁、制表符、█ ▒ ·）
DejaVu Sans Mono     —— ░ ▚ ▞
Noto Sans Mono CJK   —— ╎
Adwaita Mono         —— 全部盲文（波纹 5.2%，唯一同时"只画选中的点"且"点阵铺满格子"的）
```

被淘汰的字体**不是坏字体**，只是不适合"一格一个字符"的画面。

### 两个渲染细节

**字形从不被横向压扁。** 终端不会缩放替代字形；而把 DejaVu 的盲文压进更窄的格子，
点距会被调制约 50% —— 对一个整幅都由点构成的 MV，那是肉眼可见的两点周期条纹。
所以字形按原始尺寸画在格子原点上，超出部分裁掉。

**制表符和方块保留 1px 溢出边。** `█` 在 52px 下墨迹是 x[-1..31]（格子 32px），
边缘是抗锯齿的（156/255、176/255）。裁掉溢出边，每个接缝就成了一条比方块暗
三分之一的发丝线；留 1px 溢出、让相邻字形叠一下，接缝落差从 35% 降到约 12%
（剩下的 12% 是字体自己的抗锯齿边，真终端也一样）。

### 规格与产物

```
--scale 4  ->  格子 32 x 60  ->  180 x 54 个字符 = 5760 x 3240，正好 16:9
```

```sh
python3 mv/tools/render_video.py                    # 默认就是这个规格
python3 mv/tools/render_video.py --scale 2          # 2880x1620，快四倍
python3 mv/tools/render_video.py --bench 120        # 只测速，不编码
python3 mv/tools/render_video.py --sheet 27         # 只出一帧 PNG（可用来核对字体）
python3 mv/tools/render_video.py --start 59 --end 64
```

> `--sheet` 会**从头把每一帧都放一遍**再截取。`Show` 是流式驱动的：标题卡的上字、
> 幽灵抽帧、粒子场都依赖累积状态，直接跳到某个时间点会**渲染出没有标题的假帧**
> （实测：冷跳 t=27 只有 12 个方块，顺序播到 t=27 有 205 个）。

产物是 `world.execute(me).tty-mv.mp4`：H.264 high / CRF 16 / preset slow / yuv420p，
音轨 AAC 256k，`+faststart`（可直接拖进度、可网页流播）。

**速度**：光栅化是瓶颈。PIL 每次 `draw.text` 都会重新栅格化 TrueType 字形，
一帧要重复几千次；改成**字形图集**后每个字符只渲一次到 8 位掩码，再用 `paste`
（C 层混合）贴上去。5760×3240 下每帧约 **58 ms**，光栅化整片约 **6 分钟**，
端到端（含编码）约 **20 分钟**。

## 4.5 音乐放哪，以及没有音乐怎么跑

**音乐不在仓库里。** 那是一张商业唱片，`*.ogg *.mp3 *.flac *.m4a *.wav *.opus`
全部已 gitignore（`.spectrogram.png` 也一样 —— 频谱图是从那首曲子渲出来的派生图）。

### 想听真声：把文件放进来

把音轨放在**仓库根目录**（就是有 `play.sh` 的那一层）。这片子当初测量的那个文件叫：

```
world_execute(me)_-Mili-9893117-192.ogg
```

用这个名字、放这个位置，**不需要任何参数** —— `find_track()` 会在项目里递归找
`*.ogg/*.mp3/*.flac/...`，第一个命中的就是它。放别的名字也行，只要后缀是上面那些；
也可以直接指名：`./play.sh /path/to/your.ogg`。

放好之后第一次跑会花几秒做一遍 STFT 测量，结果存进 `mv/cache/*.npz`
（716 KB，已 gitignore，可随时删掉重算；`--rebuild` 强制重算）。

> 缓存里没有音频采样，只有每帧的频段能量、onset、节拍这类数字。
> 想在不带唱片的情况下复现**完全一致**的画面，把那个 `.npz` 一起提交就够了。

### 没有音乐：stand-in 模式

**没有音轨也能跑。** 不会报错，也不会卡住 —— 它改用一份 **stand-in 乐谱**：

```
./play.sh                       # 找不到音轨就自动进入 stand-in
./play.sh --no-music            # 音轨在也强制用 stand-in（调试用）
```

stand-in 不是"随便糊一个假数据"，它是**从这片子自己写死的那些事实推出来的**：

| 来源 | 内容 |
|---|---|
| `shots.py` 已经硬编码的 | 130.000 BPM、拍相位 0.1254 s —— 镜头网格本来就按拍子对齐，有没有音轨都一样 |
| `scenes.py` 的幕表 | 15 幕的起止时间，每一幕的响度权重（副歌/执行最响，虚空/失去最轻） |
| 曲子本身的长度 | 211.91 s，音乐在 207.48 s 结束 |

于是**写下来的东西全都照常发生**：每一幕、每个镜头、标题卡、字幕、进度条，
全部落在原本的时间点上、落在正确的拍子上。**只有"跟着声音动"的那部分安静下来** ——
频段能量、瞬态、闪光强度 —— 因为那正是一份 stand-in 拿不到的东西。

实测吻合度（同一时刻，60×18 网格，逐格对比真实测量渲染的结果）：

| 时间 | 幕 | 逐格相同 |
|---|---|---|
| 5.0 s | boot | 91.2 % |
| 30.0 s | geometry | 89.5 % |
| 62.0 s | chorus | 67.4 % |
| 150.0 s | execution | 82.8 % |
| 200.0 s | void | 88.8 % |

副歌差得最多（67 %）是应该的 —— 那一幕的画面几乎全部由频谱驱动。

**它不会假装自己是测量结果**：`--list` 会打印 `NOT MEASURED: built from the
piece's own act table and tempo`，启动时也会在 stderr 说明，
缓存里的 `source` 字段写的是 `"stand-in"` 而不是音轨路径。

播放时钟同时降级：`make_clock()` 拿不到音轨就用 `WallClock`（单调时钟），
所以没有声音也不会去启动 mpv。

## 5. 依赖

| 依赖 | 用途 | 缺失时 |
|---|---|---|
| `python3` + `numpy` | 分析、渲染 | 必需 |
| `ffmpeg` | 解码 + 测量 | 必需（首次生成缓存时） |
| `mpv` | 播放 + **真实播放头**（IPC `time-pos`） | 降级为单调时钟，画面与声音可能缓慢漂移 |
| 音轨文件 | 测量、驱动频谱/瞬态 | **不影响运行**：自动改用 stand-in 乐谱，全程静音（见 4.5） |

`mpv` 走 `--input-ipc-server`，每 200 ms 回读一次真实播放位置，
所以画面跟的是声音而不是墙上时钟 —— 卡顿、拖动进度条之后都不会失步。
`--ao` 可以透传给 mpv（例如 `--ao null` 做无音频输出测试）。

## 7. 哪些是实测，哪些不是

写清楚，免得把工程当成魔法：

- **实测**：速度 130.000 BPM、拍相位、21 个段落切点（已吸附到瞬态）、417 个瞬态点、
  频段能量、波形包络、音乐实际结束于 207.48 s（文件尾巴有 4.4 s 数字静音，MV 用它演完关机）。
  每一幕的图形尺寸、脉动、闪烁都挂在这些数字上。
- **有出处**：歌词文本与时间戳、专辑与作者信息。*（未在本机听音核对 ——
  时间戳来自与这份 .ogg 同一版母带的官方曲库条目，时长逐毫秒吻合。）*
- **我写的**：幕表（哪段配哪个图形）、全部图形与变形、配色、字体与排版、故障/闪光等演出效果、
  **第二个实体的整条路径**（故事线），以及**那张 14 个词的 cue 表**。
  后两者都是取舍而不是转录 —— 但它们不能脱离音乐：
  `selftest.py` 会断言每个上屏词的时刻都精确等于官方歌词的某一行，
  也会断言故事线的每个关键节点（登场 / 相遇 / 离去 / 归来 / 消失）。
- **不是实测**：**stand-in 乐谱**（没有音轨时的替身，见 4.5）。
  它由上面那些**作者写下的事实**推出来 —— 幕表、130.000 BPM、拍相位、曲子长度 ——
  不是从录音里量出来的，所以它只保证"写下来的东西照常发生"，
  不保证频谱、瞬态这些跟着声音动的部分。缓存里 `source` 字段写的是 `"stand-in"`，
  启动和 `--list` 都会说明；它不会被当成测量结果用。
- **已知取舍**：长词在矮窗口里降到 scale 1 分行；再放不下时退化为普通文本，
  宁可变小也不把词切一半。极小的终端（<46 列）图形会变得很简，这是尺寸的物理限制。

## 8. 终端怪癖（都踩过，都留了回归测试）

`python3 mv/tools/selftest.py` 会断言下面这些不变量，改坏了立刻会红：

**① 帧里一个换行符都不能有。** 播放在 raw 模式下跑，`tty.setraw()` 会清掉 `OPOST` ⇒ `ONLCR` 失效 ⇒
`\n` 是**不带回车的换行**。光标于是停在最后一列、armed 自动换行标志，
而各终端对"这个待换行要不要先兑现"的处理并不一致：**Konsole 先兑现**，于是每行多吃一行，
画面纵轴正好拉长一倍（xterm 会丢弃该标志，所以在别处看着是好的）。
现在每行都用 `ESC[r;1H` 绝对定位、完全不发换行。

**② 右下角那一格在虚拟控制台上不写。** 碰到右下角就滚屏的终端会让整个画面每帧上移一行 ——
看上去就是"一直在刷屏"。这条只在 `TERM=linux`（即 `caps.is_console`）时生效：
图形终端不会因为这个滚屏，白白留出一格反而在右下角留个黑洞。

**③ 绘图不能覆盖帧底色。** `put()` 的 `bg` 默认是"保持原样"（`KEEP` 哨兵），
否则每个字形都会把终端默认底色打进画面，在大字上表现为一条条竖直细缝。

**④ 光束的横竖比例要对。** 终端格高约为宽的两倍，所以屏幕上一条直线在格子坐标里
y 的步进必须是 x 的一半。比例写错时，"放射光束"会糊成一条条水平虚线，看着像扫描线故障。

**⑤ 文字是导演不是转录。** 断言上屏词总数 ≤ 30、占时长 < 45%、且每个时刻都落在官方歌词行上。

**⑥ 复位只在故障收尾，且只有三次。** 断言复位恰好 3 次、每次都在长故障段的末尾
（且不在段中）、单次刷白 <0.75 秒、全片累计 <1.8 秒、其余任何时刻复位等级恒为 0，
并且**真的把画面洗白**（复位峰值处的平均背景亮度 > 关闭时的 1.8 倍）。

**⑦ 标题只显示一次。** 这一条是**扫出来的**，不是假设的：全片每 0.2 秒渲染一帧，
找出"某一行的字形块横跨 ≥60 列"的帧（就是大字），把连续帧并成窗口，
断言**只存在一个长度 >1.5 秒的窗口**，且它落在 `title` 幕里。
起因是一个真 bug：标题卡曾经被画两遍 —— `title` 幕画一次，
`TEXT_CUES` 里又有一条 16.000 的标题，于是两个不同宽度的标题叠在一起。
（顺带：预览剧照也曾经因为采样把 13 秒的标题卡放进两张图，看起来像有两个标题；
现在剧照改成一幕一张，不再重复。）

**⑧ 代码流要盖过标题。** 断言 `title` 幕的背景模式是 `rain`，且 25 秒处仍有 ≥20 个雨点字形。

**⑨ 撕裂只在故障段和断音处。** 除了上面的故障段断言，还断言
**14 处断音全部落在官方歌词行上**、重复词 / 重复句 / 连字符三种形态都能抓到、
每段撕裂 ≤0.5 秒、全曲覆盖 <6% 的帧；而"两次断音之间"与"故障段之外"渲染出的帧
与关掉撕裂**逐字节相同**。

**⑩ 撕裂只在故障段。** 断言 12 个撕裂时刻全部落在官方歌词行上、
峰值强度 ≥0.9、三段之外**撕裂等级恒为 0**（采样 424 个点）、三段之内始终 >0.2，
并且**真的动了画面**：判决处 ≥1/4 的行发生位移，而正常段落与"关掉撕裂"渲染出的帧**逐字节相同**。

**⑪ 漂浮光点不许穿过主体。** 第二个实体的路径被重新布线：
除**相遇那一段**（`MERGE_SPAN = (52.5, 72.5)`，两人合一本身就是剧情）之外，
它到中心的距离始终 ≥ 0.91 —— 而主体大致占 `r ≤ 0.9`。
最麻烦的是 1:20 附近它要从左边换到右边：直线过去正好穿过画面正中，
所以拆成一段**绕过主体的弧线**（82.0 / 83.5 / 85.0 / 86.5 四个途经点）。
断言：合并窗口以外没有任何采样点落在主体半径内、满不透明度时不会跑出画面。
它的显示也重做了：**外圈碎光环（bloom）+ 四段缺口的细环（reticle）+ 实心核心 + 一个高亮像素**，
在空画面和满画面上都看得清。

**⑫ 不许跟着拍闪。** 整屏闪白（`_postfx` 的 flash）**已删除**；
**整帧背景色带**（跟着 bass 走的全局染色）做了两件事：一是**重度平滑**
（一阶滤波，时间常数约 0.7 s，实测帧间最大跳变 7/765，肉眼不可见），
二是**在虚拟控制台上整个关掉** —— 16 色会把小变化量化成离散跳变，而慢终端上重刷每一格的背景
看起来就是整屏在闪。断言：整帧最大亮度跳变 ≤ 24/765；
控制台上"背景必须等于该幕的基色，且不随音乐变、不在调色板项之间跳"。
连字幕压暗也从"瞬间切换"改成**按 7/s 的速率渐入渐出**（原来每条字幕出现时整帧亮度会猛跳一下）。
节拍冲击波从"任何强瞬态都触发、0.55 秒走完"改成"只应最大的那几个、2.2 秒慢慢扩开、最小间隔 2.4 秒"；
图形尺寸、粒子、字幕辉光、第二个实体、进度条统统改成读**平滑量**（bass / rms / 频谱质心），
不再读 onset / beat。**音频反应没有取消，取消的是频闪。**

**⑬ 平放的进度条必须是少数。** "20% 概率平放"听起来合理，实际抽出来是
**35% 平放 + 8% 倾角小到看不出（<5.7°）= 42% 看起来是平的** —— 因为 n 只有 52，
伯努利抽样运气偏差就有 ±5%。改成**按构造定数**：全局打乱一个恰含 14% 为真的标志表，
再分配到每条，实测 **7/52 = 13%**；同时把倾斜幅度的下限设成 0.13 rad，
所以**没有一条落在"看得出是斜的"和"平的"之间的灰带里**。
语义/长度/粗细/边框/出现时段完全不动（保留一次同长度的占位抽样，确保随机数流不变）。

**⑭ 进度条不许退回成播放进度。** 断言所有进度条的语义都在
`section / phrase / beat / energy / story / cue` 之内（加回 `duration` 就会红），
外加"部分镜头才有 / 一条镜头可有多条 / 长短粗细有变化 / 有平放有倾斜 / 多数带框"。

**⑮ 长句要撑到下一次开口。** `ILLEGAL ARGUMENTS` 用
`HOLD_TO_NEXT_VOCAL` 一直挂到 147.660（下一句 `EXECUTION`），共 16.4 秒；
断言"下一句开口前它还在、开口后被换掉"。**挂这么久当然不能是静止的**：
0.15 秒打印完之后它开始**缓慢呼吸与横向摇摆**（周期与拍不同步），
所以是"活着"而不是一张静帧。

**⑯ 字号要有上限。** 巨型字幕曾经铺满整屏，把底下的画面全压住了。
现在它只能占**屏宽的一部分**（`TYPE_WIDTH_FRACTION = 0.52`，标题卡 0.78），
断言"≥120 列时占宽 ≤55%、80 列时 ≤70%"——
80 列那条是物理底线（9 个字母在最小点阵就是 53 格），不是回归。

**⑰ 场景不能退化，长幕不能是一张图。** 断言场景中位数 ≤3.8 s、场景数 ≥60、
**每个长幕至少 3 个场景**、有词的幕里每个场景起点都落在官方歌词行上
（器乐段除外，它按实测段落切）、且**至少 60% 的场景有东西跑出画面边界**。

**⑱ 场景表不能退化。** 断言场景数 ≥55、最长 ≤5.5 s、最短 ≥1.0 s、
同一母题不连续出现、母题库确实用满、没有哪个母题霸屏、机位有变化，
且**每条镜头边界要么是已发布歌词行、要么是实测拍点**。

**⑲ 小字层不许跑到中间。** 断言每个闪现锚点都在外圈
（`|x-0.5| > 0.20` 或 `|y-0.5| > 0.28`）、微字体确实是 3×5 且比大字体窄、
每个闪现词的时刻都落在官方歌词行上、且不与大词的时刻撞车。

**⑳ 开头要像真的开机，三个名字要藏在里面。** 断言启动日志同时用上 dmesg / systemd /
包管理器三种排布、至少 30 行、至少 10 行带内嵌进度条、进度条样式不止一种；
并且 **Aperture / Mili / dsh 各自至少两种写法、且各自出现在不止一种 register 里**
（不能只塞在一行里），
并且**在某行的时间槽开始 0.25 秒后，整行文字必须已经在屏幕上**（这一条就是在盯"逐行而不是逐字"）。

**㉑ 故事线不能悄悄断掉。** 断言：开场时第二实体不在、标题卡时两人都在且相距很远、
第一次副歌时两人重合、审判幕之前它已经离开、爱那一幕它回来但**在心形之外**、关机前彻底消失。

## 8.5 歌词的处理

**这个仓库不分发歌词。** `lyrics/world.execute(me).lrc` 里每个 cue 只保留
**那一段的第一个字母**（`[00:00.100]S`），时间和结构一个不少，文字一个不留。
两条 credits 行（作曲/作词）原样保留 —— 那是署名，本来就该跟着走。

完整歌词留在本地 `lyrics/world.execute(me).lrc.full`，**已 gitignore**；
后缀排序在 `.lrc` 之后，所以「取第一个 `*.lrc`」拿到的仍然是发布的那份。

### 为什么断音表要烤进代码

断音检测原来是**运行时**从歌词文字里读的（重复词、连续重复行、连字符字母串）。
歌词一压成首字母，它就**什么都读不到** —— 而这个仓库跑起来会因此
**少掉 14 处撕裂**，等于放出一部不一样的片子。

所以那 14 个时刻现在是 `shots.STUTTER_TIMES` 里的**数据**。
歌词退回它本来的位置：**对照物**。完整歌词在手时，
`selftest.py` 会 `stutter_cues_from_lyric()` 重推一遍，和表里的数字对不上就 FAIL。

### 自检会跳过什么

需要**歌词文字**才能做的三条检查（重复词 / 重复行 / 连字符串确实被抓到），
在没有完整歌词时会明确打印 **`SKIP`** —— 不是静默通过。
`SKIP` 会在结尾汇总里再点一次名，免得它看起来像 PASS。

## 8.6 撕裂时间轴（`mv/ttymv/tears.py`）

**撕裂什么时候发生、多强，只由这一个文件决定。** 它不读歌词、不读分析缓存、不读音频。

```
tears.EVENTS     12 个失败瞬间（illegal arguments / executions / 结尾）
tears.FLOOR      三幕各自的地板，让"故障"是一段时间而不是几下点击
tears.STUTTERS   14 处人声断音
tears.RESETS     3 次重置闪光
```

### 人声到底有多少断音：**零**

这不是猜的，是**五种检测器都落空**之后得出的：

| 检测器 | 结果 |
|---|---|
| 中频带凹陷（180 Hz–3 kHz 短时下陷） | 那 14 个时刻处只有 **3–8 dB**，而一次真正的断音要 >12 dB —— 什么都没发生 |
| 频谱**原样重触发**（60–300 ms 滞后） | 相似度 ≥0.90 的帧：**0 个**，任何阈值都是 0 |
| **亚拍 onset**：onset 间隔短于半拍 | 全曲 417 个 onset 的中位间隔 **461 ms**，拍长 **462 ms** —— 节奏严丝合缝；短于半拍的只有 **2 对** |
| 滑动自相关找**重复乐句** | 是连续谱，**没有可分的类**：阈值取 0.30/0.35/0.40/0.45 分别给出 30/17/6/1 个"事件" |
| 6–30 Hz **门限/切音**（只看纯浊音窗） | 同样是连续谱：p50=0.485、max=0.935，最强的 12 个窗口只有中位的 **1.58 倍** |

结论：**这段录音里没有音频层面的断音。** 歌里那 14 处是**写下来的重复** ——
一行里重复的词、连续三行说同一件事、以及一个用连字符拆开的字母串；
它们是**照常唱出来的**，不是被切碎的。

所以效果就落在这 14 处：每处一段 300 ms 的滑移，强度 0.58–1.00（见
`tears.STUTTER_SPAN` / `SHAPE`）。这条早先的记录仍然成立、也被重新证实了：
*"试过用音频检测，在这个编曲上不可靠"* —— 不是不可靠，是**根本没有那个现象**。

### 为什么必须内部化

早先撕裂强度里混进了两个外部量，两个都拆掉了：

- **音乐的粗糙度**（`flux` + `high`）—— 同一时刻，载入哪份分析就撕得不一样
- **实测凹陷**（`gaps`）—— stand-in 乐谱**根本没有** `gaps`，
  于是**有音乐和没音乐渲出来的撕裂不一样**。这已经是一个真 bug 了。

现在 `tear.(level|stutter_level|glitch|reset_level)` 全是纯函数。
不变量盯着这件事：**同一时刻，测量音轨与 stand-in 的撕裂曲线逐点相同**，
并且用 AST 检查确认这些函数**碰不到任何分析数据**。

> 教训：**决定"什么时候发生什么"的东西，要放在一个读不到外界的地方。**
> 读得到，就会漂。

`tears.calibrate()` 是它的校准：9 条，全部对着**本仓库自己的幕表**，
不对着歌词也不对着音频 —— 每个瞬间都在该失败的那一幕里、地板撑满整幕、
平静处严格为零、间距不成周期、不与拍网格重合、重置永远跟在故障之后。
